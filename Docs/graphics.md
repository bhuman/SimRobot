# Graphics in SimRobotCore3

`SimRobotCore3` renders the scene for the 3D views, for exporting images and for the camera-like sensors (`Camera`, `DepthImageSensor`, `ObjectSegmentedImageSensor`). Everything that draws goes through the class `GraphicsContext` (and the helpers in `Graphics/Primitives.h`); only the 3D view widget (`SimObjectWidget`) and the renderer (`SimObjectRenderer`) know which graphics API is used.

## Graphics APIs

The graphics API depends on the platform:

| API | Platforms | 3D view | Controller drawings | Multisampling | Shadow maps |
|-|-|-|-|-|-|
| OpenGL 4.5 core | Linux, Windows | `QOpenGLWidget` | yes | yes | yes |
| Metal | macOS (Qt >= 6.7) | `QRhiWidget` | yes | yes (4x, in the 3D view and in exported images) | yes |

CMake defines `SIMROBOTCORE3_USE_OPENGL` or `SIMROBOTCORE3_USE_METAL` for `SimRobotCore3` and for its interface target `SimRobotCore3Interface`, because the signatures of `SimRobotCore3::Renderer` depend on it (with Metal, they take the native handles of a `QRhi` instead of using the current OpenGL context).

OpenGL is deliberately used via `QOpenGLWidget` (also where Qt is new enough for `QRhiWidget`), since sharing contexts with the offscreen renderer and drawing external content into a `QRhiWidget` does not work reliably with OpenGL. The long-term plan is to use Vulkan (via QRhi, which requires Qt >= 6.7) on the other platforms as well, but the system Qt on Linux is older on some machines.

## Structure

- `Graphics/GraphicsContextBase.{h,cpp}`: everything that does not depend on the API. It owns the CPU side of vertex/index buffers, meshes, textures (loaded with `QImage`), surfaces, model matrices (and their stacks), the clear color, the global ambient light and the lights, including the shadow maps of lights with a `ShadowMap` element (the matrices come from `Graphics/LightSpace`), and the readback buffers of the sensors. `layoutResources` determines the layout of the global vertex and index buffers and the indices of textures and surfaces.
- `Graphics/OpenGL/GraphicsContext.{h,cpp}` and `Graphics/Metal/GraphicsContext.{h,cpp}`: derive from the base class and create the GPU resources, generate the shaders from the light descriptions (GLSL and MSL), and implement the render passes: `startRendering`/`draw`/`finishRendering` inside of `startOffscreenRendering`/`finishOffscreenRendering` (images for sensors, see below) or `startExternalRendering`/`finishExternalRendering` (the 3D view), plus `updateShadowMaps`.
- Projection matrices always follow the OpenGL conventions (clip space depth from -1 to 1); the Metal context corrects them.

`Graphics/GraphicsContext.h` includes the context of the selected API, so the rest of the code just uses `GraphicsContext`. A new API needs its own directory, an entry there and in `Make/CMake/SimRobotCore3.cmake`.

## Draw lists

Everything that is made of meshes (appearances, physics, sensor shapes, the coordinate system and the drag plane) is drawn through draw lists; only controller drawings (below) are drawn differently, because their contents change in every frame. `draw(mesh, model matrix, surface)` cannot draw directly. It only records, while `GraphicsContextBase::getDrawList` calls a function that does the usual traversal the first time something is requested (`GraphicalObject::drawAppearancesCached`, `PhysicalObject::drawPhysicsCached`, or any code with its own key). A list is identified by a `DrawListKey`: an object and a variant, e.g. the render flags that decide which physics are drawn. Therefore, what is drawn for a key may only depend on the key, and nothing in the scene may change it after `compile`.

The recording is turned into batches: the instances of meshes with the same geometry (buffers with identical contents share their memory since `layoutResources`) are drawn with one instanced call, opaque ones sorted by vertex type, texture (only if the API has to bind textures itself, i.e. OpenGL) and mesh, transparent ones in the order of drawing after them. The depth-only variant ignores the surfaces, so it has fewer batches. The list is replayed (`drawList`) by every camera, view and shadow map. It contains only indices: the shaders read the model matrix (an array of the model matrices of all usage classes, which `updateModelMatrices` keeps up to date and the API copies to the GPU when it changed) and the surface of each instance from the instance data of the list.

A list does not contain any state of the render pass. The shaders (lighting, textures, shading, wireframe), the camera and the render target are set by `startRendering` before a list is drawn, so the same list can be drawn into any pass. Each pass of a list has a `native` handle for what the graphics API creates from it (the instance buffer for Metal and OpenGL). In Vulkan, this would be a secondary command buffer that is recorded once and executed by the primary command buffer of each camera, view or shadow map after the render pass begins and the camera uniforms are bound. The model matrices and instances would be storage buffers; the model matrices need a ring of buffers because the CPU writes them while earlier frames may still be in flight.

## Sensor images

The sensors that render the scene request a `GraphicsContextBase::ReadbackBuffer` per image (with its format: RGB, YUYV or depth, and its size) when they are created. Its memory is shared between the GPU and the CPU (OpenGL: a persistently mapped buffer, Metal: a buffer with shared storage) and stays at the same address, so the sensor reading points directly into it. Between `startOffscreenRendering` and `finishOffscreenRendering`, `readOffscreenImage` records which rows of the render target are converted into which readback buffer. `finishOffscreenRendering` converts them with compute shaders (with the top row first; YUYV with the BT.601 coefficients in fixed point, depths into distances along the viewing direction), submits everything and returns the number of the submission without waiting for it. `waitForOffscreenRendering` waits until a submission has been completed (OpenGL: a fence, Metal: the command buffer).

`Sensor::Port::getValue` waits for the submission of the current reading. `ImageSensorPort` (the port of `Camera` and `ObjectSegmentedImageSensor`) renders the images of several sensors of the same kind and size on top of each other into one render target, each with its own readback buffer. `renderCameraImages` only starts this, so a controller can start the rendering of all cameras early in a simulation step and read the images later. `DepthImageSensor` renders a spherical projection in several parts and resamples their distances on the CPU after waiting for them.

## Controller drawings

A controller (like the one of B-Human) can attach flat-colored 3D primitives to physical objects of the scene with `setDrawing(key, SimRobotCore3::Drawing&&)` (see `SimRobotCore3.h`). A `Drawing` consists of lines, dots, quads, spheres, ellipsoids, cylinders/cones and images (RGBA pixels) and a transformation into the coordinate system of the object. Instead of the pixels, an image can have a function that computes them when the image is drawn for the first time, so a controller that sends images faster than they are drawn (e.g. camera images that must be converted) does not convert the ones that are never drawn. The controller does not have to know about the graphics API. A drawing can be set from any thread and is removed with `removeDrawing(key)`.

`setDrawing` only moves the drawing into the `DrawingStore` of the object, whose lock only protects the map. A drawing is prepared when it is drawn for the first time (in the thread that draws the scenes, without the lock of the map), so drawings that are replaced more often than the scene is drawn are mostly never prepared. It becomes a `GraphicsContextBase::PreparedDrawing`, which is not changed afterwards: lines, dots and quads become vertices, spheres, ellipsoids and cylinders become instances of a unit sphere and a unit cylinder (whose ends the vertex shader scales by the radii of the cylinder, which also makes cones), and the pixels of the images are moved into it (or computed by their functions), each image with a new id.

For each frame, `SimObjectRenderer` collects the shared pointers of the drawings of the displayed objects (and their transformations into the world) in a `GraphicsContextBase::DrawingList` and draws it with `prepareDrawings`, `drawDrawings` and `finishDrawings` of the graphics context. `prepareDrawings` copies the vertices and the instances of all drawings into one buffer each, and `drawDrawings` draws the instances of each drawing with one draw call per mesh (the first instance of the drawing is the base instance). The textures of images are cached by their ids: an image is uploaded when it is drawn for the first time and its texture is released when its drawing does not exist anymore (the next time `prepareDrawings` is called). With OpenGL, the cache is shared by the contexts of a share group; with Metal, a command buffer retains the textures it uses until it has been completed. The alpha of the primitives is blended with a factor per pass. The passes implement the occlusion modes of the 3D view: with occlusion, the drawings are depth tested against the scene; without it, `clearDepth` is called before so that they are drawn on top; with transparent occlusion, they are drawn depth tested with their full alpha, then the depth buffer is cleared and they are drawn again with half of the alpha. The options of a drawing (`disableDepth`, `disableTransparency`, `disableOpacity`) are evaluated per pass. Drawings are never lit or shadowed.
